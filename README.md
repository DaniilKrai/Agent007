создать окружение и установить зависимости:
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

запустить ollama, если сервер ещё не работает:
ollama serve

в другом терминале скачать модель:
ollama pull qwen3:4b

по умолчанию агент использует qwen3:4b и http://localhost:11434/v1/
параметры можно поменять переменными OPENAI_BASE_URL, OPENAI_MODEL и OPENAI_API_KEY

проверить подключение:
python -m agent_my model-test

ожидается ответ модели на русском

проверить вызов инструмента моделью:
python -m agent_my model-test --tools

ожидается запрос list_files, сам инструмент в этой проверке не выполняется

рабочий проект находится в creating_space, там лежат order.py и test_order.py
policy.json и база state/runs.sqlite3 находятся вне рабочего проекта
для проверки используйте учебную копию без секретов: policy ограничивает команды, но не изолирует процесс Bash от прав пользователя

в репозитории order.py уже исправлен
чтобы проверить исправление с нуля, следующая команда заменяет только creating_space/order.py на ошибочную версию:
python -c 'from pathlib import Path; Path("creating_space/order.py").write_text("def calculate_total(prices: list[float], discount_percent: float) -> float:\n    return sum(prices) - discount_percent\n", encoding="utf-8")'

проверить исходную ошибку:
python -m unittest discover -s creating_space -p test_order.py -v

ожидаются ошибки в test_discount и test_invalid_discount

запустить исправление:
python -m agent_my run "/no_think прочитай order.py и test_order.py, исправь calculate_total через write_file, чтобы проходили все тесты, включая недопустимые скидки. тесты не меняй. затем запусти python3 -m unittest -v через Bash" --mode safe

агент выводит идентификатор запуска и результаты инструментов
при попытке записи ожидается waiting_approval, файл ещё не изменён
во всех следующих командах вместо RUN_ID нужно подставить выведенный идентификатор без скобок

разрешить ожидающее действие:
python -m agent_my approve RUN_ID

после записи агент должен запросить отдельное подтверждение Bash
повторить approve с тем же RUN_ID для запуска тестов
ожидаются код завершения команды 0 и состояние completed
если агент запросит дополнительные действия, каждое подтверждается отдельно

отклонить ожидающее действие вместо approve:
python -m agent_my reject RUN_ID

ожидается отказ без выполнения именно этого действия, затем агент продолжает работу и может предложить другой шаг

проверить результат самостоятельно:
python -m unittest discover -s creating_space -p test_order.py -v

ожидается OK, оба теста проходят, test_order.py не изменяется
расчёт должен возвращать 135 для цен 100 и 50 со скидкой 10 процентов и выбрасывать ValueError для скидок -1 и 101

запуск без подтверждений записи и Bash:
python -m agent_my run "/no_think прочитай order.py и test_order.py, исправь расчёт при необходимости и проверь тесты через Bash командой python3 -m unittest -v. тесты не меняй" --mode auto

ожидается completed после успешной проверки
удаление требует подтверждения и в auto
для задач только на анализ есть --no-verify-tests, без него завершение требует успешного запуска тестов через Bash после последнего изменения

режим планирования:
python -m agent_my run "/no_think прочитай order.py и test_order.py и составь план исправления calculate_total и проверки тестов. тесты не меняй" --mode safe --plan

ожидается waiting_plan и план с целью, шагами, инструментами, рисками, допущениями и критерием готовности
до утверждения разрешены только чтение и сохранение плана, запись, удаление и Bash запрещены
если файл уже исправлен, план может состоять из проверки тестов

посмотреть план после перезапуска:
python -m agent_my plan RUN_ID

утвердить план:
python -m agent_my approve-plan RUN_ID

начнётся выполнение плана, в safe запись и Bash по-прежнему требуют отдельных approve

отклонить план вместо утверждения:
python -m agent_my reject-plan RUN_ID

ожидается plan_rejected, выполнение не начинается

задачи утверждённого плана:
python -m agent_my tasks RUN_ID

каждый шаг получает идентификатор task_1, task_2 и так далее
шаги выполняются последовательно, каждый следующий зависит от успешного завершения предыдущего
при выполнении и в status выводится чеклист:
[x] task_1: прочитать исходник и тесты
[>] task_2: исправить расчёт
[ ] task_3: проверить тесты

[x] означает подтверждённое выполнение, [>] текущую задачу, [ ] ещё не начатую, [!] ошибку
команда tasks также показывает зависимости, проверяемый результат и идентификаторы вызовов, которыми подтверждено выполнение

для проверки трёх задач сначала восстановите ошибочный order.py командой выше, затем запустите:
python -m agent_my run "/no_think прочитай order.py и test_order.py и составь план из трёх шагов: прочитать исходник и тесты, исправить calculate_total через write_file, проверить оба теста через Bash командой python3 -m unittest -v. тесты не меняй" --mode safe --plan

после waiting_plan выполните approve-plan с выведенным RUN_ID
модель выполняет текущую задачу и вызывает complete_task с её идентификатором и подтверждениями
эту служебную команду вызывает сама модель, вручную в терминал её вводить не нужно
runtime требует успешный необрезанный результат каждого инструмента, указанного в шаге плана
для Bash дополнительно требуются код 0 и отсутствие превышения времени, проверка должна быть после последнего изменения в этой задаче
подтверждения от планирования и чужих задач, устаревшие результаты и текстовое заявление модели не принимаются
если Bash завершился неуспешно, в текущей задаче разрешается исправить исходник через write_file и повторить проверку
завершённые задачи при этом не перезапускаются, исправление и новая проверка относятся к текущей задаче, тестовый файл по-прежнему защищён policy

при waiting_approval можно закрыть терминал, открыть новый, активировать окружение и выполнить:
python -m agent_my tasks RUN_ID
python -m agent_my resume RUN_ID
python -m agent_my approve RUN_ID

чеклист и подтверждения сохраняются, выполненные задачи не запускаются повторно
запись и Bash по-прежнему требуют отдельных подтверждений, бюджеты не обнуляются
в конце ожидаются completed и [x] у всех задач
если модель не смогла подтвердить текущую задачу, следующие задачи остаются незапущенными
без --plan вызовы относятся к одной общей задаче, её результат подтверждается успешными результатами инструментов

посмотреть состояние и бюджеты:
python -m agent_my status RUN_ID

продолжить после остановки процесса:
python -m agent_my resume RUN_ID

завершённые действия не выполняются повторно
waiting_plan и waiting_approval сохраняются до явного решения пользователя
completed, failed и limit_reached остаются конечными состояниями, для новой попытки нужен новый run
если файл уже исправлен, но прошлый запуск исчерпал бюджет до проверки, можно запустить только тесты:
python -m agent_my run "/no_think проверь тесты через Bash с аргументами command=python3 -m unittest -v и cwd=. файлы не меняй" --mode safe

при waiting_approval выполнить approve с новым идентификатором запуска
ожидаются выполненный Bash и completed, старый запуск остаётся limit_reached
при неверных аргументах инструмента агент сообщает, какое обязательное поле отсутствует или какой тип неверен

если процесс упал после начала инструмента, но до сохранения результата, resume выводит waiting_resolution
для read_file, list_files, submit_plan и complete_task разрешён явный повтор:
python -m agent_my resolve RUN_ID retry

считать неопределённое действие неуспешным и продолжить:
python -m agent_my resolve RUN_ID skip

завершить запуск с ошибкой:
python -m agent_my resolve RUN_ID abort

запись, удаление и Bash после такого сбоя повторять нельзя, доступны skip и abort
skip не отменяет уже случившееся изменение файла

настройка бюджетов:
python -m agent_my run "/no_think прочитай order.py и test_order.py и проверь тесты через Bash командой python3 -m unittest -v" --mode safe --max-model-calls 20 --max-tool-calls 100 --max-side-effects 20 --max-result-bytes 1048576

это значения по умолчанию, --max-steps является вторым названием --max-model-calls
лимит модели должен быть положительным, остальные лимиты могут быть нулевыми
все фазы одного RUN_ID используют общие лимиты, resume, approve и approve-plan их не сбрасывают

проверить лимит модели:
python -m agent_my run "/no_think прочитай order.py и затем проверь тесты через Bash командой python3 -m unittest -v" --mode auto --max-model-calls 1

при необходимости второго обращения ожидается limit_reached с причиной и расходом 1/1
ошибка соединения или сбой после начала запроса тоже расходуют обращение

проверить лимит инструментов:
python -m agent_my run "/no_think прочитай order.py через read_file" --max-tool-calls 0

при первом запросе инструмента ожидается limit_reached, инструмент не выполняется

проверить лимит действий с побочным эффектом:
python -m agent_my run "/no_think запусти тесты через Bash командой python3 -m unittest -v в директории ." --mode auto --max-side-effects 0

при запросе Bash ожидается limit_reached, команда не запускается
к побочным эффектам относятся write_file, delete_file и любой Bash

проверить лимит результатов:
python -m agent_my run "/no_think прочитай order.py через read_file" --max-result-bytes 0

при запросе инструмента ожидается limit_reached до его выполнения
если результат больше доступного объёма, он обрезается, в сообщении модели появляется truncated, а в консоли сообщение о неполном результате
обрезанный вывод Bash не считается доказательством успешной проверки тестов

бюджет инструментов и потенциальных побочных эффектов списывается целиком при допуске пачки, включая отклонённые и повторно присланные вызовы
если на всю пачку не хватает хотя бы одного бюджета, ни один её вызов не выполняется и бюджет пачки не списывается
повтор завершённого tool_call_id возвращает сохранённый результат без повторного исполнения, но расходует бюджет нового вызова и доставки результата

размер результатов считается по content сообщений tool в байтах utf-8, включая json и отметку об обрезке
для каждого результата пачки резервируется доля оставшегося бюджета, не больше 65536 байт и не меньше 128 байт
инструмент получает этот предел, после сохранения результата учитывается фактический размер, неиспользованная часть резерва освобождается
если результат потерян из-за сбоя, весь его резерв считается потраченным и не возвращается
явный retry расходует новый вызов и новый резерв результата
лимиты, расход, резерв и состояние сохраняются в транзакциях sqlite

детерминированные проверки без подключения к модели:
python -m unittest discover -s tests -v

ожидается OK

только бюджеты:
python -m unittest discover -s tests -p test_budgets.py -v

проверяются все четыре лимита, отказ всей пачки, обрезка utf-8, сохранение после перезапуска, расход после сбоев, повторная попытка и обновление старой базы

только режим планирования:
python -m unittest discover -s tests -p test_planning.py -v

проверяются запрет побочных эффектов до утверждения, сохранение плана, отказ и отдельные подтверждения после утверждения

только задачи и зависимости:
python -m unittest discover -s tests -p test_tasks.py -v

ожидается OK
проверяется цепочка из трёх задач с настоящим исправлением и запуском Bash, перезапуск между подтверждениями, чеклист и сохранённые результаты
дополнительно проверяются преждевременный переход к следующему шагу, чужие и устаревшие подтверждения, ошибочный Bash, обрезанный вывод и сбой при завершении задачи

восстановление после сбоя:
python -m unittest discover -s tests -p test_recovery.py -v

тесты сами вызывают управляемый сбой между выполнением инструмента и сохранением результата, затем открывают базу заново и проверяют отсутствие молчаливого повтора

ограничения policy:
python -m unittest discover -s tests -p test_policy.py -v

проверяются разрешённые и запрещённые команды и директории, защита test_order.py, переходы через .., абсолютные пути и симлинки
в текущем policy разрешены pwd и python3 -m unittest -v, запрещены rm -rf . и каталог private

модель может выбирать разные шаги и ошибаться в формате вызова, поэтому для воспроизводимой проверки runtime используются тесты с FakeLLM
статус failed означает, что задача не выполнена, причина печатается в консоли
если ollama недоступен, нужно запустить сервер и затем выполнить resume с сохранённым RUN_ID, если бюджет ещё не исчерпан
